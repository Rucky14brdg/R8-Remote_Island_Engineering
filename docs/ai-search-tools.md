# 離島工学AI：検索操作を分担する設計

2026-11-11。現在の検索方式。通常の検索ではLLMにSPARQLを書かせない。

## 分担

- LLM：話題の語句と目的の抽出、追加で調べたい情報の選択、取得資料の解釈と回答。
- システム：登録項目の検索、RDFの関係方向、正しいSPARQLの生成と実行、本文の取得、検索状態の管理。

標準モデルは `qwen3.5:4b` のまま。回答用の共通プロンプトは短いまま維持し、字数・節構成・引用形式の強制は追加しない。DBを書き換えず、外部サービスも検索しない。

## LLMが選べる操作

| 操作 | 引数 | システムの処理 |
| --- | --- | --- |
| `find_entities` | `terms` | 名前・表示名・別名・概要・説明・記事本文を、全種類の項目から検索 |
| `get_related` | `ids`, `relation` | 関係方向と型を管理したSPARQLで関連項目を取得 |
| `read_documents` | `ids`, `offset` | 項目の説明本文、記事本文、出典付き記述等を取得 |
| `answer` | `reason` | 取得結果と本文を確認して回答へ進む |

`get_related` の種類は `researches`, `issues`, `technologies`, `articles`, `records`, `members`, `all`。実績・目標・根拠・出典の取得は `records` で行う。生のSPARQLを渡す操作は受け付けない。

取得結果には登録されたid・名前・型・関連経路を返す。名前と内部IDを混同しないよう、システムがidを解決する。存在しないidや曖昧な同名項目を推測でURIに変換しない。

## 最低限の検索手順

「保育所に関する研究」は、話題「保育所」、目的「関連研究」として扱う。「研究」は最初のタイトル検索条件にしない。

1. 話題を全種類の項目から探す。名前の一致を、本文だけの一致より優先する。
2. 施設・課題・技術・資源・記事などの候補を起点に、目的に合う関連項目を取得する。
3. 関連研究が見つかった場合は、研究別の参加者・役割と、その研究に紐づく記事を取得する。
4. 研究・記事の本文を読む。
5. LLMが必要に応じて、技術、追加の参加記録、実績・根拠、本文の続きなどを追加取得する。

基本の検索と本文取得はシステム側で実施するため、モデルが早く回答したがっても、候補の名前だけで終わらない。基本取得後も、未確認の主要項目があれば本文確認を求める。一覧だけの質問では登録された型から一覧を取得する。

施設から研究を探す際には、次の両方の経路を使う。

- 研究 → 対象とする → 施設
- 施設 → 抱える → 課題 ← 解決を試みる ← 研究

技術・資源・参加者・組織・記事・根拠などを起点にした関連研究の経路もシステム側で定義する。共通の教員がいることだけで、施設に関する研究へ別の研究を混ぜない。RDFの関係が増えた場合は、この対応をシステム側で更新する。

## 語句と別名

原文から取れる語句と登録名を使った検索を優先する。見つからない場合は、LLMが補った検索語でも検索する。既存の原文の話題が見つかる場合、無関係な言い換えで候補を広げない。

登録データの `別名`・`略称` を検索できる。初期の語彙辞書 `search_aliases.json` には、送り迎え→送迎、坂道→坂の／急坂／急勾配、すれ違いに関する表現→離合、保育園→保育所を登録した。これは語句の対応であり、特定の研究名や回答を固定する辞書ではない。未知の表現をすべて理解するものではなく、必要に応じて語彙を拡張する。

## 状態と本文確認

- `sufficient`：主要な取得項目の本文を確認して回答へ進んだ。
- `partial`：候補が多いなどの理由で、主要項目の一部だけ本文を確認した。
- `no_match`：検索操作は成功したが、今回の条件で指定種類の関連項目を取得できなかった。DB全体にないという意味ではない。
- `tool_error`：必要な検索操作を完了できなかった。該当データがないという意味ではない。
- `limit`：検索操作または判断の上限に達し、調査が完了していない。
- `not_needed`：挨拶など、検索する登録情報の話題が指定されていない。

各操作でも、候補なし・本文未登録・引数不正・クエリ実行失敗を分ける。空の検索結果や、候補を探しただけの結果を、読めた資料の参照元へ数えない。本文を読んでいない候補は、登録名・概要などの範囲で扱う。画面の「検索の過程」には実行した操作と、システムが生成したSPARQL・取得結果の件数を表示する。

## 運用上限

1質問で最大8操作。基本取得の後の判断は最大5回。最初に本文を読む主要項目・記事は最大8件。関連項目は最大40行、話題候補は20件まで。本文は1操作で1項目につき1400文字×4チャンクまで取得し、続きがあれば `next_offset` を返す。部分取得を表示し、LLMは追加取得できる。

読取専用のクエリ実行は `sparql_search.py` の既存実行器を使用する。外部アクセス・更新を拒否し、1クエリ5秒で打ち切る。SQL風の文字や引用符を含む検索語はRDFリテラルとしてエスケープする。

## 検証

84件のPythonテストとAI画面のJavaScript検証に成功。特に「保育所」「送り迎え」「坂道」の質問では、研究タイトルに検索語が含まれない状態でも、施設・課題を起点として目的の研究へ到達し、関連記事の本文を確認できることを検証した。同じ教員に関係する無関係な研究が混ざらないことも確認した。

実DBと実際の `qwen3.5:4b` でも3例を実行した。

| 質問 | 取得した主要研究 | 研究・記事の本文確認 | 全体の所要時間 |
| --- | --- | --- | ---: |
| 保育所に関する研究について、知っている限りを教えてください | 交互交通制御の研究1件 | 研究1件・関連記事2件 | 62.02秒 |
| 送り迎えに関する研究はありますか | 同じ研究1件 | 同上 | 42.85秒 |
| 坂道に関する研究を知りたい | 同じ研究1件 | 同上 | 43.47秒 |

いずれも基本4操作で、検索操作はすべて成功し、目的の研究を取得した。時間は本文生成まで含む1回ずつの実測で、性能保証ではない。[実行結果](evaluations/ai-search-tools-2026-11-11.json)。回答文の全主張の正確さを保証する評価ではない。

既存の会話には変更前の誤った回答が残るため、動作確認ではページを再読み込みし、新しい会話を使用する。会話・研究・記事の既存データはこの変更で削除しない。

## 研究参加者と記事著者の区別（2026-11-11修正）

`members` は研究→参加関係→主体をたどり、参加記録の役割・活動を研究ごとに保持する。活動が別の研究を指す記録は使わない。旧形式の直接担当関係は、同じ研究・人物の参加記録がない場合に限って使う。基本検索に参加記録の確認を追加したため、施設→研究→参加記録→記事→本文の5操作となる。

回答資料では研究の参加者・役割を明記し、記事の著者は執筆者として別に示す。記事著者の参加記録が当該研究で確認されていなければ、その確認範囲も示す。取得失敗や未確認は「参加者なし」と扱わない。別研究での参加歴や共通の所属から参加者を補わない。著者・参加者の登録データは変更しない。

86件のPythonテストとAI画面のJavaScript検証に成功。記事著者が別研究の参加者である場合、研究間で教員の役割が異なる場合、取得失敗の場合を追加検証した。
