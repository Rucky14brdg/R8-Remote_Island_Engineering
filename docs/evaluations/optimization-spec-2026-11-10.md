# 取り消し済みの最適化仕様

2026-11-11にリセット済み。以下は過去の記録で、現在の動作を表さない。

## 用途別の回答と根拠照合（2026-11-10）

### 目標

地域の困りごとから研究を探す、技術や考え方を理解する、記事を読む、知見の他地域への活用を検討する、という操作を支援する。もっともらしい長文より、質問に合う短い回答、研究単位で正しい関係、計画と実績の区別を優先する。

### 質問と会話の扱い

- 用語説明：一般的な定義・仕組み・具体例と、DB内での利用例を分ける。前者は「モデルの知識」と明示し、DBの参照番号を付けない。登録されていない用語も一般説明は可能だが、最新性・専門的な仕様の正確さを保証しない。
- 研究探索：現在の質問から参照元を選ぶ。明示された研究名があるときは、その研究と関連する記事・根拠・参加記録に絞る。幅広い研究一覧の質問では研究候補を一覧から取得する。
- 記事読解：明示された記事本文だけを読む既存仕様を維持する。
- 活用相談：登録情報と「活用の案・確認したい条件（AIの考察）」を分ける。転用の効果・実証結果を創作しない。
- 前の質問の検索語・取得項目を無条件に混ぜない。指示語を含む続きの質問だけ直前のユーザーの質問と候補を使う。前のAI回答本文は事実の材料として再投入しない。
- 複数の研究を提示した後の「この研究」など、対象が一つに定まらない質問には対象を確認する。

### 検索範囲

登録名の直接一致、本文の検索、RDFの実在する関係を組み合わせる。直接見つかる質問には検索語抽出用のLLM呼び出しを追加せず、候補がないときだけ構造化出力で言い換えを補う。無関係な質問をDB全体へ代用しない。

用語説明では用語自身と、その用語を直接参照する研究のみを取得する。別の技術、共通の教員の他研究、関係のない記事へ展開しない。通常の探索も、途中にある人物・組織・地域・技術などの共有項目からさらに拡散せず、参加記録の「活動」から未選択の研究へ越境しない。

文量には上限を設け、抜粋・省略を表示する。検索範囲外の項目への関係を、識別子だけの曖昧な説明としてモデルへ渡さない。検索は網羅性を保証せず、「今回参照した範囲」として回答する。

### 回答を表示するまで

1. モデルは最大6段落のJSONを生成する。各段落を `registered` / `general` / `proposal` に分類する。
2. `registered` の段落には参照番号と、10文字以上の根拠原文を必須とする。サーバーが実在する参照番号と、参照本文内の原文との一致を確認する。組版上の空白・全半角・読点の違いだけは正規化する。
3. 本文の参照番号はモデルの文字列を使用せず、照合済みの番号からサーバーが作る。一般説明は用語説明時だけ、活用案は活用相談時だけ許可する。
4. 照合できない段落は省略して表示する。使える段落がない・JSONとして不正な場合は一度だけ再構成を試み、それでも照合できなければ登録情報の原文抜粋に切り替える。
5. 未確認の生成文や内部JSONは画面に流さない。生成中は進捗を表示し、照合後に本文を表示する。中止・通信エラーは従来どおり扱う。

`grounding` は `matched`（段落の参照箇所を照合）、`partial`（照合できない段落を省略）、`extractive`（原文抜粋）のいずれか。これは引用箇所の存在を示すだけで、段落内の全主張の意味的一致・情報の最新性・一般説明の正確さを保証する判定ではない。出典に戻って確認する導線を維持する。

### 生成・運用

ローカルOllamaを維持し、外部への資料送信、モデルの自動ダウンロード、DBの自動更新は行わない。生成温度は0.1、検索計画・再構成は0、コンテキストは16,384、記事の出力は1,500トークン、その他は2,200トークンを上限とする。thinkingはfalseとして、最終回答とは別の推論過程を画面に出さない。

APIの `timings` に検索・生成・合計の時間、`grounding_repaired` に再構成の有無を記録する。モデル変更と検索改善の効果を分けて評価できるようにする。

構造化出力とthinkingのパラメーターはOllama公式の [Structured outputs](https://docs.ollama.com/capabilities/structured-outputs) と [Thinking](https://docs.ollama.com/capabilities/thinking) を参照した。

### 再現可能な評価

`scripts/eval_island_ai.py` で実DBを変更せず、研究一覧・一覧後の用語説明・計画と実績・新しい地域への話題変更・他地域への活用・未登録の実績を比較する。`--models`、`--cases`、`--output` で条件を指定できる。回答・参照元・検索語・待ち時間・照合状態をJSONに保存する。自動検査だけで意味の品質を合否判定せず、保存した回答も人が確認する。


### RDFから直接返す回答と用語資料

単純な研究一覧と、施設に紐づく課題一覧は、LLMに転記させずRDFの関係・保存された概要から直接表示する。複数の研究の参加者や手法を総論として混ぜない。`grounding=direct` とし、画面には「登録データ」と表示する。

RDF・SPARQLの基礎説明には `ai_glossary.py` の、公式資料に基づいて編集した短い用語資料を優先する。モデルの生成でも不正確なトリプル例が出たために追加した参照資料であり、LLMの一般知識が改善したと見せるものではない。出典は [W3C RDF 1.1 Primer](https://www.w3.org/TR/rdf11-primer/) と [SPARQL 1.1 Query Language](https://www.w3.org/TR/sparql11-query/)。用語資料のある単独の基礎説明は `grounding=curated` とし、画面にも「用語資料・登録データ」と表示する。比較・最新規格の質問はこの定型説明に置き換えない。

DBでの利用例は、用語を直接参照する研究との実際の関係と、保存されている研究概要を使って別に組み立てる。その他の用語の一般説明はモデルの知識として表示する。施設・人物・研究・課題そのものの説明を、一般知識による用語説明へ流さない。外部の出典リンクはサーバーで定義した上記2つのURLだけを許可し、モデルが生成した外部URLは引き続きリンク化しない。

### モデル選択と制約

このPCの既存モデルを実測した。4Bモデルは短い回答が可能な一方、研究の混同、不自然な用語説明、計画を完了済みに変える表現、繰り返しが残った。12Bモデルは初期比較の計画・実績の整理でより慎重な回答が得られたため標準とした。ただし一般説明や引用の照合には失敗もあり、厳格な意味検証に合格したモデルという意味ではない。

26Bモデルも試したが、この環境では初回の回答待ちが長く、約2分で比較を中断した。回答品質の優劣は判断していない。コード向け14Bモデルの比較、クラウドモデルの比較、モデルの追加学習は未実施。既存会話で選択済みのモデルは保持し、新しく開く会話は12Bを標準とする。

86件のPythonテストと、AI画面・ホーム・Markdown・地図のJavaScript検証を実施。話題変更時の候補リセット、明示研究への絞り込み、施設の課題だけの取得、複数研究の曖昧な指示語への確認、過去の生成文の除外、原文照合、生成文を表示する前の確認、照合失敗時の抜粋、一般説明とRDF利用例の分離を含む。Chromeでも新しい会話の標準モデルと、用語資料・研究との実関係・参照番号を表示するRDFの回答を確認した。

複雑な要約・活用相談は、依然として数十秒から1分以上かかる場合がある。照合できない段落の省略や抜粋への切り替えも発生する。事実の主語や意味の完全な一致を保証する仕組みではなく、今後の改善対象として回答・参照元・時間を再現可能な形で評価する。
